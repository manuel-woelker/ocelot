# What is a nominal effect declaration?

A nominal effect declaration introduces an effect name that functions may mention in `can` and `cannot` clauses.
Effects are lightweight labels, not executable statements.

`can` does not mean mere permission.
It means the function explicitly declares that this effect may originate at that function.
`cannot` is the opposite restriction: the function body and anything it reaches must not have that effect.

# What rules should readers assume first?

For the first version of the spec:

- effects are declared as `effect <name>;`
- user-defined effect names must be declared before they can be used in function effect clauses
- `can <effect>` explicitly declares or introduces that effect on the function
- `cannot <effect>` forbids that effect from the function body and everything it reaches
- a function may declare both clauses, and `can` must come before `cannot`
- effects propagate upward through function calls
- builtin effects exist without user declarations:
  - `write_stdout` for `println()`
  - `panic` for `assert()` and `assert_eq()`

This keeps the initial model narrow and nominal.
There are no effect variables, effect polymorphism, or effect lists yet.

# What do `can` and `cannot` mean on a function?

`can <effect>` is an explicit effect declaration on the function.
It marks the function as one place where that effect may be introduced.

`cannot <effect>` is a checked prohibition.
It does not just forbid the effect on the current line.
It forbids the effect from the whole reachable function body, including effects that arrive through called functions.

# What does an effect declaration look like?

## Example: a file can declare one nominal effect

main.ocelot-script:

```ocelot
effect exec;
fun child() can exec {}
fun parent() {
    child();
}
```

```text
```

# How do effects propagate through calls?

If one function has an effect, callers inherit that effect transitively.
That is true both for explicitly declared `can` effects and for builtin effects introduced by called functions.

## Example: a caller inherits a callee's declared effect

main.ocelot-script:

```ocelot
effect exec;
fun child() can exec {}
fun parent() {
    child();
}
parent();
```

### Output

```text
```

## Example: builtin effects do not need explicit declarations

main.ocelot-script:

```ocelot
fun log() {
    println("hello");
}
fun check() {
    assert(true);
}
log();
check();
```

### Output

```text
hello
```

# What happens when a function forbids an effect?

A function with `cannot <effect>` must not directly or transitively have that effect.

## Example: `cannot` rejects transitive effect propagation

main.ocelot-script:

```ocelot
effect exec;
fun child() can exec {}
fun parent() cannot exec {
    child();
}
```

### Error


## Example: `cannot` rejects effects through multiple call layers

main.ocelot-script:

```ocelot
effect exec;

fun leaf() can exec {}
fun middle() {
    leaf();
}
fun root() cannot exec {
    middle();
}
```
